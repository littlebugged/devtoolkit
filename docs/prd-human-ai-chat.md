---

## 1. 背景与目标

### 1.1 背景

希望做一个轻量 Web 应用：一方以「问 AI」的方式提问，另一方以「AI」身份回复；双方都清楚对面是真人，「AI 人」可以用 AI 口吻逗对方。系统负责在线匹配、会话粘性分配，并持久化问答记录。

### 1.2 产品目标

1. 打开页面即可选择角色，开始文字互动。
2. 提问时自动分配给一名**当前在线**的「AI 人」。
3. **同一 session 内的追问优先粘住同一 AI 人**。
4. 完整存储用户发出的问题与收到的回复，可按会话追溯。
5. 在 Cloudflare / GitHub **免费额度**内可运行（两人到小规模闲玩场景）。

### 1.3 非目标（本期不做）

- 真实大模型自动回复
- 音视频、图片/文件消息
- 完整账号体系（OAuth、手机号登录等）
- 多端 App / 原生推送
- 内容审核与风控中台
- 付费会员、广告、运营后台（可后续迭代）

##  2. 角色与术语


| 术语              | 定义                                       |
| --------------- | ---------------------------------------- |
| 提问者（Asker）      | 选择「询问 AI 问题」的用户，发起问题并接收回复                |
| AI 人（Responder） | 选择「假装 AI 回复别人问题」的用户，接收被分配的问题并以文字回复       |
| Session（会话）     | 提问者侧一次连续对话上下文；首问创建，后续追问归属同一 session      |
| 在线              | AI 人保持与服务端的有效连接（WebSocket 或等价心跳），可被分配新问题 |
| 粘性绑定            | 某 session 已绑定的 AI 人；追问优先仍分给该人            |


说明：双方**知道对面是真人**；「扮 AI」是互动玩法，不是欺骗系统身份。

---



## 3. 用户故事

1. **作为访客**，我打开页面能看到两个明确选项，快速进入对应角色。
2. **作为提问者**，我发送问题后能看到回复（或等待中状态）；追问时尽量还是同一个人接。
3. **作为 AI 人**，我上线后能收到分配给我的问题，并回复；可同时处理系统分配给我的会话（MVP 可限制为串行）。
4. **作为任一角色**，我希望历史问答被保存，刷新后仍能看到本 session 的记录（在合理保留期内）。

## 4. 核心流程



### 4.1 入口与角色选择

```
打开页面
  → 选项 1：假装 AI 回复别人问题 → 进入 AI 人待命页（标记在线）
  → 选项 2：询问 AI 问题         → 进入提问聊天页
```

- 同一浏览器可切换角色；切换时需明确结束/暂停当前角色状态（如 AI 人下线）。
- MVP：同一时刻一个浏览器标签页只扮演一个角色。



### 4.2 提问与分配

```
提问者发送消息
  → 若为 session 首问：创建 session，从「在线 AI 人」池分配一人并绑定
  → 若为 session 追问：优先分给已绑定且仍在线的 AI 人
  → 若绑定 AI 人已离线：从在线池重分配，更新绑定，并提示提问者「对接人已更换」（可选文案）
  → 若无人在线：进入等待态（见 5.3）
  → 消息落库，推送给目标 AI 人
```



### 4.3 回复

```
AI 人收到问题 → 输入回复 → 发送
  → 消息落库，推送给对应提问者
  → 提问者会话中展示为「对方回复」（可用中性/AI 风格 UI，但不隐瞒真人属性）
```



### 4.4 下线

- AI 人关闭页面、心跳超时或主动离开 → 标记离线，不再接收新分配。
- 其已绑定 session：后续追问触发重分配（见上）。
- 提问者离开：session 可保留历史；是否允许 AI 人继续回复离线提问者的消息——MVP 规定：**仅在线推送，离线不补发**；历史仍可查。

## 6. 分配规则（规范说明）

伪代码：

```
on AskerSend(session, message):
  persist(message)

  if session has no binder:
    responder = pickOnlineResponder()
    if responder is null:
      enqueue(session, message)
      notifyAsker(WAITING)
      return
    bind(session, responder)
  else if binder(session) is offline:
    responder = pickOnlineResponder()
    if responder is null:
      enqueue(session, message)
      notifyAsker(WAITING)
      return
    rebind(session, responder)
    notifyAsker(RESPONDER_CHANGED)  // 可选
  else:
    responder = binder(session)

  pushTo(responder, message)
  notifyAsker(DELIVERED_OR_PENDING_REPLY)

on ResponderOnline(responder):
  markOnline(responder)
  while hasCapacity(responder) and hasQueuedSessions():
    session = dequeueFIFO()
    bind(session, responder)
    pushPendingMessages(session, responder)
```

**追问定义（MVP）**：同一提问者、同一 `sessionId` 下，在已有至少一条已发送问题之后的后续消息，均视为追问，走粘性逻辑。

## 7. 信息架构（页面）

1. **首页**：标题 + 玩法一句话说明 + 两个入口按钮
2. **提问者聊天页**：消息流（我 / 对方）+ 输入区 + 状态条（等待分配 / 等待回复 / 对方已更换）
3. **AI 人工作台**：在线开关/状态 + 当前待回复列表 + 选中会话的消息流 + 回复输入

视觉与品牌：本期以功能可用为主；若并入现有站点，遵循现有设计系统。

| 合规  | 娱乐向 UGC；页面声明用户内容自负；后续可加举报入口                                              |

## 9. 技术方案边界（产品侧约束，非详细设计）

- **前端**：静态站点，部署 Cloudflare Pages（源码在 GitHub）。  
- **后端**：Cloudflare Worker；会话协调与在线池可用 Durable Object；消息持久化可用 DO SQLite 或 D1。  
- **实时**：WebSocket（Worker / DO）；必要时轮询降级。  
- **身份**：MVP 用本地生成的 `clientId` + 昵称；不强制登录。

详细表结构、接口、方案对比见后续《技术设计文档》，不在本 PRD 展开。

## 10. MVP 范围与里程碑



### 10.1 MVP（必须交付）

- 双角色入口  
- 在线分配 + session 追问粘性 + 离线重分配  
- 无人在线排队等待  
- 纯文本收发与历史存储（当前 session 可恢复）  
- 免费栈可部署运行



### 10.2 下一步（可排期）

- 昵称与简单口令房  
- AI 人多会话并发上限与负载均衡（最少负载分配）  
- 等待超时与取消  
- 简单管理页：查看队列长度、在线人数  
- 内容长度/频率更严格的限制与基础敏感词

## 11. 成功标准

1. 两名用户分别选两种角色，可完成「提问 → 分配 → 回复 → 追问仍为同一人」完整路径。
2. AI 人断开后，提问者追问会分给另一在线 AI 人（若有）。
3. 刷新提问者页后，仍能看到本 session 历史消息。
4. 在免费额度内完成一次公开演示部署。
